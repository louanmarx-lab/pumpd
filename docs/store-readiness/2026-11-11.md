## Confirmed blockers and high-priority defects

### R1 — Billing and purchase restoration are simulated

**Priority: release blocker for a paid launch.**

Evidence: [inAppPurchaseService.ts](/Users/lou-anmarx/Pumpd/src/services/inAppPurchaseService.ts:22) waits 800 ms and returns an active subscription. `productId` is calculated but never sent to a store. Restoration waits 600 ms and returns success; no UI calls `restorePurchases`. [SeatUpgradeModal.tsx](/Users/lou-anmarx/Pumpd/src/components/coach/SeatUpgradeModal.tsx:128) accepts the fabricated result, while its footer claims Apple/Google billing. Local role changes can also grant active plan state. Package dependencies contain no native billing integration. The mock probe confirms the false-success behavior.

Remediation: either launch an explicitly free product with paid UI/claims disabled, or integrate native purchases, store product prices, verified backend entitlements, restoration, cancellation, renewal, expiry, refund/revocation handling, and subscription management. Custom seat pricing needs a real catalog/billing design; arbitrary local prices cannot stand in for store products.

Acceptance: sandbox purchase/cancel/restore/renew/refund on both stores; reinstall restores the verified entitlement; no entitlement is granted after a failed or cancelled transaction. Review any regional billing exceptions against intended distribution. [Apple payment guidance](https://developer.apple.com/app-store/review/guidelines/), [Google Play payments](https://support.google.com/googleplay/android-developer/answer/9858738).

### R2 — No account and associated-data deletion flow

**Priority: store blocker.**

Evidence: [authService.ts](/Users/lou-anmarx/Pumpd/src/services/authService.ts:82) supports registration but has no account deletion. Settings offers local test-log clearing and reset, not account deletion. [clearAllData](/Users/lou-anmarx/Pumpd/src/context/UserWorkspaceContext.tsx:2651) leaves Firebase Auth and cloud records intact. It is not an erasure mechanism.

Remediation: an easy-to-find authenticated deletion request with reauthentication where needed, server-side cleanup of the account's owned data and subcollections, shared claims/rooms and coach relationships, local drafts/caches, clear retention handling, and a completion/failure state. Delete data before removing the identity needed to authorize cleanup, or use a secure server job. Also provide a functional web deletion-request page for Google Play. Clarify treatment of intentionally exported copies held by other users.

Acceptance: delete a disposable test account; verify its backend records and credentials are removed, other users' records survive, and relaunch cannot restore deleted data. A failed deletion must not say success. [Apple deletion requirements](https://developer.apple.com/support/offering-account-deletion-in-your-app/), [Google deletion requirements](https://support.google.com/googleplay/android-developer/answer/13327111).

### R3 — Missing in-app privacy, legal and support entry points

**Priority: privacy-policy blocker; subscription disclosures also need completion.**

No privacy policy, terms/EULA, or support links were found in signup, Settings, or purchase UI. This app handles identity, fitness, nutrition, body measurements, coach-client records and shared workouts.

Remediation: publish accurate, accessible policy/support pages and link them from the app and store metadata. Describe Firebase processing, coach/buddy sharing, local-only data, exports, retention, deletion, and contact details. Complete Apple App Privacy and Google Data safety from a verified data inventory, including SDK behavior. Store-console declarations were not inspected. [Apple privacy disclosures](https://developer.apple.com/app-store/app-privacy-details/), [Apple policy-link requirement](https://developer.apple.com/app-store/review/guidelines/), [Google User Data policy](https://support.google.com/googleplay/android-developer/answer/10144311).

Acceptance: links load publicly; actual data flows match disclosures; consent and sharing explanations are visible where needed; subscription terms and restoration are reviewable.

### R4 — Shared workout rooms have a tiny, collision-prone PIN space

**Priority: security and reliability release gate.**

Evidence: [useGymJam.ts](/Users/lou-anmarx/Pumpd/src/hooks/useGymJam.ts:435) chooses a number from 10–99: only 90 possible rooms. [gymJamService.ts](/Users/lou-anmarx/Pumpd/src/services/gymJamService.ts:120) writes directly to that PIN's document without a uniqueness transaction. Joining reads and updates the same record without a transaction or a client-side occupancy check.

Consequences: simultaneous hosts can select the same document; join races can replace guest information. Whether unauthorized reads/writes are allowed depends on deployed rules, which were not inspected. A PIN is not sufficient authorization.

Remediation: high-entropy room identities/invitations, atomic room creation and participant admission, short expiry, host approval or authenticated membership, rate limits, and server-enforced participant permissions. Verify rules with allowed and denied cases, including stranger access, guest replacement, expired rooms and revoked access. Do not relax rules to make guest demos connect.

### R5 — Cloud errors can be reported as success

**Priority: reliability release gate.**

Evidence: [firestoreService.ts](/Users/lou-anmarx/Pumpd/src/services/firestoreService.ts:44) catches write failures for profiles, nutrition, metrics, coach records, splits and deletion without rejecting. [syncAllToCloud](/Users/lou-anmarx/Pumpd/src/context/UserWorkspaceContext.tsx:1068) can consequently reach `synced` despite failures. The probe reproduces swallowed permission-denied errors. Workout saving correctly rejects and is an exception to this finding.

Room creation similarly returns `waiting` after a denied write, leaving users waiting for a room that was never created.

Remediation: explicit operation results/errors, durable retry tracking, per-account pending state and accurate aggregate sync status; return room creation failure. Avoid declaring all data synced after just one successful write.

Acceptance: deny each write category in isolation, go offline/relaunch/reconnect, retry, and verify actual records plus status. No lost or falsely backed-up data.

### R6 — Cloud deletions do not converge across devices

**Priority: data-integrity release gate.**

Evidence: [workspace subscriptions](/Users/lou-anmarx/Pumpd/src/context/UserWorkspaceContext.tsx:800) merge cloud workouts/metrics into prior local state and ignore empty snapshots. Nutrition merges old meals into the cloud snapshot and uses maximum water volume. A removed record/meal or lowered water total can persist on another phone; manual sync can write stale entries back. Local “Clear Test Logs” does not remove cloud records.

Remediation: authoritative ownership-aware reconciliation with pending local changes and deletion tombstones/versioning, rather than additive merges alone. Define local reset separately from cloud deletion.

Acceptance: two-account/two-device tests for delete-last-workout, remove-meal, reduce-water and offline conflicts; no deleted entries return after relaunch or manual sync.

### R7 — Coach linking requires server-authorized atomic validation

**Priority: security verification gate.**

Evidence: [clientClaimService.ts](/Users/lou-anmarx/Pumpd/src/services/clientClaimService.ts:84) generates four-character Math.random codes and copies health/identity history into claim records. Claim execution performs separate writes and catches several failures. Local claimed/expiry checks cannot establish authorization or atomic single-use redemption.

Remediation: trusted server redemption, stronger invitation tokens, atomic single-use/expiry enforcement, minimal pre-redemption disclosure, explicit consent, and rule tests for unrelated users, concurrent redemption, coach unlinking and revoked access. Preserve progress/retry safely during partial failures.

This is a source design concern and missing security evidence, **not a demonstrated production data breach**.

### R8 — Release identity, toolchain and native artifacts remain incomplete

**Priority: build/submission gate.**

[app.json](/Users/lou-anmarx/Pumpd/app.json:15) lacks `ios.bundleIdentifier`. Expo introspection substitutes `com.placeholder.appid`, which is not a chosen release identity. The production EAS profile requests an Android app bundle, but signing, store app records, version history and an actual build were not verified. The preview profile pins Node 20.18.0; installed Expo/RN engines require supported Node 22/24/26 ranges. Production inherits no explicit Node pin, so its actual image must be checked separately.

Remediation: choose/register the intended bundle ID, confirm the existing Android package identity, pin supported toolchains, verify version/build increments against store records, validate generated icons and privacy manifests, and inspect signed release artifacts. Source icon transparency is a validation risk; no generated icon upload was tested. Introspection's debug-style values do not prove a final archive's deployment target or transport security settings.

Acceptance: signed IPA/AAB builds and installs; validate actual target API, iOS SDK, manifests and 16 KB compatibility. Apple currently requires Xcode 26+/iOS 26 SDK for uploads; Google mobile new apps/updates require target API 36+. [Apple build requirements](https://developer.apple.com/news/upcoming-requirements/), [Google target API](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en-GB), [Android page sizes](https://developer.android.com/guide/practices/page-sizes).

## Additional pre-release work

- **Permissions:** QR scanning does not need audio. `app.json` explicitly includes `RECORD_AUDIO`; Expo camera plugin defaults enable it. Set `recordAudioAndroid: false`, remove unnecessary declarations, and inspect the final manifests. Introspection also shows legacy storage permissions and an iOS microphone purpose string; determine whether the final binary needs them. Test denied camera permission and manual PIN entry. [Expo camera configuration](https://docs.expo.dev/versions/latest/sdk/camera/).
- **Health features:** complete the Play Health apps declaration for exercise/nutrition features. Review automated nutrition claims, add accessible source information and appropriate non-medical scope language, and avoid presenting generic defaults as individualized clinical advice. Classification, target ages and store text need review. No medical accuracy assessment was performed. [Health declaration](https://support.google.com/googleplay/android-developer/answer/14738291?hl=en), [Health content policy](https://support.google.com/googleplay/android-developer/answer/16679511?hl=en).
- **Production UX:** gate or replace “Clear Test Logs” and “Reset Defaults” with truthful user-facing controls. Existing reset preserves the current identity; the reviewer suggestion that it necessarily replaces a signed-in user with Alex was not substantiated. Test VoiceOver/TalkBack, large text, keyboard dismissal, Android Back, small screens and iPad (tablet support is enabled).
- **Review materials:** public privacy/support/deletion URLs; accurate screenshots and descriptions; age/content rating and data declarations; a functioning review account and two-user instructions for trainer/shared-session features. Offline guest demos exist but do not establish end-to-end cloud review access.
- **Testing access:** if the Play developer account is a personal account created after 13 November 2023, check its closed-testing requirement: 12 opted-in testers for 14 consecutive days before production access application. Account type/history is unknown. [Google testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en-GB).
- **OTA preference:** no update was sent. Existing native config still enables Expo Updates/check-on-launch and a preview channel. Decide the intended production update policy explicitly; the audit did not alter it.

## Required final testing and release sequence

1. Resolve R1–R3 and server authorization/data-integrity defects R4–R7. Choose free launch vs real billing before implementing plan behavior.
2. Configure release identity/toolchains and least-privilege native permissions; create policy/support/deletion pages and store declarations.
3. Run automated authorization, deletion, synchronization and billing lifecycle tests against isolated test infrastructure.
4. Build signed candidates and test on real iPhone/Android plus supported iPad: fresh install, signup/login/reset, account switching, airplane-mode save/relaunch, reconnection, trainer linking/unlinking, one-phone buddy history/transfer, two-phone session, receipt/share, deletion and failed operations.
5. Test real purchases via an appropriate development/store sandbox build. **Expo Go remains useful for UI/workout testing, but cannot verify a native billing integration.** [Expo IAP guidance](https://docs.expo.dev/guides/in-app-purchases/).
6. Obtain platform validation, complete TestFlight/Play testing and review materials, re-audit the exact release candidate, then submit only with explicit user authorization.

A passing JavaScript export cannot certify signing, native launch, final SDK targets, store-console configuration, backend authorization, privacy compliance or approval. Those remain unverified until the steps above produce evidence.
